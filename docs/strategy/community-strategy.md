# Community Strategy Draft

## Community Purpose

GradEval360 needs a contributor community that can help maintain and extend a role-based evaluation platform for Graduate Assistant lifecycle work. Because the project is still early, the community strategy should prioritize clarity, onboarding, and sustainable handoff before broad outreach.

## Audiences

- Student contributors who will build features, tests, documentation, and workflow improvements.
- Tech leads and future maintainers who need enough structure to guide work across semesters.
- Client and stakeholder partners who can validate whether the workflow reflects real evaluation needs.
- Prospective users such as GAs, mentors, and administrators who can provide usability and process feedback.

## What Unites the Community

The community is united by the goal of making Graduate Assistant evaluation work more transparent, consistent, and easier to complete. Contributors and stakeholders both benefit when the workflow is understandable, status-driven, and well documented.

## What Differentiates the Audiences

- Contributors need setup clarity, scoped issues, testing expectations, and review feedback.
- Users need a product that matches their real evaluation responsibilities and does not add unnecessary administrative burden.
- Admin stakeholders need reporting, data integrity, and confidence that final evaluation records are accurate.
- Future maintainers need stable architecture, strategy documents, and decision history.

## Strategic Priorities

- Make first contribution paths obvious through labels, issue templates, and contributor docs.
- Keep project decisions documented in durable Markdown files inside the repository.
- Use user feedback from GAs, mentors, and admins to guide product scope.
- Preserve testing and review expectations so quality does not depend on one person.
- Create handoff-ready artifacts that future teams can update rather than recreate.

## Near-Term Community Actions

- Create 3 to 5 `good first issue` tickets tied to documentation, tests, fixtures, or small UI copy improvements.
- Invite feedback from at least one GA, one mentor, and one admin on the Milestone 2 workflow.
- Add short acceptance criteria to new issues so contributors know when work is complete.
- Keep checkpoint artifacts in `docs/checkpoint-artifacts/` so course evidence doubles as project memory.
- Use PR templates consistently to capture testing notes and screenshots when relevant.

## Community Health Measures

- New contributors can complete local setup using documented steps.
- Issues contain enough context and acceptance criteria to begin work independently.
- Pull requests include testing notes and link back to tracked issues.
- Strategy and architecture docs remain current as workflow behavior changes.
- User feedback leads to concrete backlog items or design changes.

## Open Questions

- Which user group needs the most support first: GAs, mentors, or admins?
- Which parts of the annual evaluation process differ by unit?
- What level of public contribution is appropriate while authentication and institutional workflow details are still stabilizing?
- Which docs should be required reading for every future contributor?
